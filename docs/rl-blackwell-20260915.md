## 移除金币扣分

按用户要求直接移除了训练采样路径中的金币扣分，没有保留系数为零的实现。删除了逐动作金币奖励计算、八个座位的逐步扣分列表、扣分计数及终局奖励拼接。采样器直接返回终局标量奖励。续训会删除旧配置中的 `unused_gold_penalty`，保存 `reward_mode: placement_only`。

协调器、训练入口和默认启动命令均不再传金币惩罚参数。第一名额外奖励保持 1，即最终第一名 +2、第八名 -1。旧冻结模型的检查点仍如实保留历史训练配置，不能通过改写历史元数据撤销已经学过的内容。

补丁位于 `scripts/enable-training-performance.py`，新服务器修改前的代码和哈希在 `/root/tavern-blackwell-20260915/runtime-backup`。补丁只在正式训练停止且成功取得训练锁时安装。

## 采样测量

同一份 256 层检查点、相同 128 个种子，每局执行 128 步，测试顺序为 32、64、128、64 并行。CUDA Graph 启用，原历史对手池、英雄池和动作预算保留。

| 并行环境 | 动作/秒 | 平均有效推理批量 |
|---|---:|---:|
| 32 | 257.83 | 3.81 |
| 64 首次 | 282.99 | 6.39 |
| 128 | 328.59 | 11.60 |
| 64 复测 | 285.86 | 6.39 |

全部种子、全部配置的动作回放一致。128 并行相对两次 64 并行均值提高约 15.5%，相对 32 并行提高约 27.4%。这是截短对局的采样测试，不能直接换算每小时完整训练局数。

## PPO 测量方法

另收集 8 局完整对局并分析采样的 CPU 耗时。PPO 分别使用序列批量 16、32、64，比较普通和融合 Adam。每个测试恢复同一份模型、优化器状态和随机种子，使用相同轨迹及原有两轮 PPO；测试更新的权重不写入正式检查点。

融合 Adam 切换时，在加载优化器状态之前覆盖参数组设置，保证旧检查点不会把融合选项恢复为关闭，也保证步数张量放到正确设备。新配置保存到正式检查点，CPU 恢复会使用普通 Adam。

较大的 PPO 批量减少每轮优化器更新次数，会改变学习过程。不能把样本吞吐增加视作棋力提升，也不能仅凭一次测试扩大模型或调整学习率。PyTorch 对融合优化器的说明见 [官方优化器文档](https://docs.pytorch.org/docs/main/optim.html)。

原始记录位于新服务器 `/root/tavern-blackwell-20260915`。正式 4 小时训练从启动时开始计时，不计迁移与测试时间。

## 后续扩大整机并行

单进程方案在 11:12:50 启动，用户随后要求进一步提高整机占用，已在 11:18 主动停止以更换采样结构，累计局数尚未增加。这次尚未完成新一轮更新；调优后重新计满 4 小时，新的停止时间是北京时间 15:50:39。

新增 `ProcessSimulationPool`，各子进程从同一检查点 inode 加载模型及历史对手，使用互不重复的种子区间，保留全局座位轮换偏移。全部轨迹收齐后由原模型执行一次 PPO，因此不会把不同策略版本的经验混入同一更新。停止时终止子进程组并清理临时数据。

测试的总并行环境保持 256，比较 1、4、8 个采样进程。单进程初始化 256 个 Node 环境触发文件描述符软上限，新实现会在硬限制允许范围内提高采样子进程的软限制。初次失败没有改写正式检查点，修复后重新运行。

CPU 分析显示大量时间用于公开状态的字段整理、JSON 处理和张量构造，单纯增加网络层数或显存占用无法解决这些等待。多进程采样使这些工作并行执行。后续重点是复用采样进程以摊薄模型与模拟器启动成本、预处理 PPO 的重复字段，以及用固定留出对局检查模型强度；累计训练局数不能代替棋力评估。


## 多进程与 MPS 结果

相同 256 个种子、每局 128 步，包含采样进程启动、模型加载、CUDA Graph 捕获及数据汇总时间。

| 采样进程 | MPS | 动作/秒 |
|---|---|---:|
| 1 | 关闭 | 247.77 |
| 4 | 关闭 | 414.31 |
| 8 | 关闭 | 285.35 |
| 4 | 开启 | 694.72 |
| 8 | 开启 | 1006.62 |
| 16 | 开启 | 1313.19 |

每组比较内部的全部动作回放一致。16 进程 MPS 的采样吞吐约为单进程的 5.30 倍；这不是完整训练吞吐的倍数。16 进程短测曾达到 25 核 CPU 配额的 100%、GPU 90%～96%、42.46 GiB 内存。MPS 的用途和工作方式见 [NVIDIA 文档](https://docs.nvidia.com/deploy/mps/when-to-use-mps.html)。

无 MPS 时，8 进程虽然显示 GPU 100%，却比 4 进程慢。不能把 GPU 忙碌率或显存占用当作训练效率。各进程的模型版本保持一致，最终按分片编号汇总轨迹，不让进程完成先后影响 PPO 的输入顺序。

16 局完整集成测试已完成一次 PPO，全部对局正常终止。共 19,264 个学习样本，78 次优化器更新，无 KL 提前停止，损失和梯度有限；测试只写独立输出目录。原始记录位于 `full-process.log`。

## PPO CUDA Graph

`--training-graphs` 为残差网络捕获前向和反向计算，编码器、GRU、损失及 Adam 仍按原流程运行。不同大小的尾部批量使用普通计算，每轮 PPO 完成后释放图。网络结构、浮点精度、优化器更新次数和排名奖励没有变化。实现依据 [PyTorch 2.12 API](https://docs.pytorch.org/docs/2.12/generated/torch.cuda.make_graphed_callables.html)。

另用相同 16 局完整对局比较，18,211 个样本、两轮 PPO、序列批量 32、融合 Adam。普通计算两次为 51.96/51.34 秒，图模式为 49.73 秒，提升约 3.9%。全部完成 74 次更新，无提前停止，最终权重最大绝对差 2.38e-7。单独测试还验证了输入梯度、连续 Adam 更新、不同大小尾部批量和恢复原始 forward。

PyTorch 在图捕获时给出了 AccumulateGrad 流不匹配的性能提示，测试没有发生捕获失败或数值异常。当前主要剩余开销仍是公开状态字段整理，图模式只带来小幅收益。

## 字段编码缓存

实际完整对局抽取 128 个公开观察，在本机分别重复打包 16 次。原计算两次用时 0.539/0.518 秒，缓存版 0.381/0.375 秒，字段打包吞吐约提高 40%。这只是 CPU 子步骤测试，不能当作整轮训练提速。全部输出张量的字节、字符串及索引一致。

数值编码使用最多 16,384 项的缓存，保留原公式和精度；正零和负零单独处理，避免 Python 浮点键相等导致符号位混合。缓存返回不可变元组，不缓存模型输出、隐藏记忆或训练梯度。

该纯计算优化在北京时间 12:00:41 原子安装，不中断在途对局。已运行的 Python 进程保留旧导入，下一次启动采样子进程时采用缓存；主学习进程在下一段训练启动时采用。即时资源截图不能证明所有进程都已切换。安装前后源码和哈希保留在服务器 `feature-cache` 目录，四小时训练截止时间不变。
