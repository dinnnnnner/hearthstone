2026-09-11 已按最新安排，将公网人机切换为当前本机推理的 64 层、680 局冻结检查点。每次推理通过 SSH 转发，公网只运行游戏逻辑。64 层四小时任务已到时结束，部署与带宽测试见 [在线推理记录](neural-serving.md)。256、1024 层仍待各自核验和接入。

本机推理转发已实现，公网默认使用 64 层模型。模型选择入口和多模型路由尚未实现；以下涉及这些功能的内容仍是后续计划。

## 训练结束后的检查

1. 确认 campaign 已结束，查看 `status.json` 和日志，区分正常到时停止、达到局数上限和异常退出。异常退出的部分产物不能标成已完成四小时训练。
2. 将最后完成的 `training/latest.pt` 复制为独立、不可覆盖的待部署文件，记录 SHA-256、完成局数、训练配置和规则版本。先备份完整检查点，再导出仅含推理所需权重和定义的文件。
3. 严格加载检查点，检查参数有限性、合法动作、序列记忆及实际更新次数。1024 层尤其需要检查 KL 提前停止频率。到点中断的一轮不能计入已完成局数。
4. 用相同的固定对手、独立种子和对局预算评估各模型。当前 campaign 的监控套件包含各自初始模型，分数不能直接作为跨深度排名。没有通过统一评估前，不使用“更强”或难度等级命名。
5. 核对线上规则、动作编号和观察格式，再进行推理压测。当前在线旧模型使用独立的旧观察投影，新模型使用观察版本 4、实体版本 3；不能只替换权重文件后共用旧输入。输入契约不匹配的模型应拒绝启用。

本轮三个训练包锁定的 sourceHash 为 `9074e697a84044483b109afa0900472cba382fbdeca99dfb01c70ef1396bb0ad`。训练期间工作区的规则修复不会自动进入这些包，部署时必须重新核对差异。

## 公网选择哪个 AI

计划在新建人机对战时选择现有模型或已验证的 64、256、1024 层模型；好友房由房主为补位人机选择模型。首次实现按房间选择，同一房间的人机使用同一个模型版本。

候选模型通过检查和资源评估后才可选择。房间创建时保存稳定的模型标识和检查点哈希，模型发布后不改变已有房间使用的版本。界面显示模型名称和实际可用状态，不把训练层数直接当成棋力等级。

服务端按房间的模型标识选择对应的观察编码和推理端点。每个房间、每个座位分别维护 GRU 状态，不能在不同模型之间复用。继续保留合法动作校验、过期响应丢弃和每回合操作预算。

推理故障时沿用已有回退处理，并让玩家知道本轮已回退为脚本人机，不能仍显示为所选模型正常对战。原有 780 局模型和脚本人机保留为恢复路径。

## 先评估公网资源

公网机器承载网页、酒馆房间和另一个游戏，不能按整机资源全部留给推理估算。现有推理服务的内存上限为 512 MiB，CPU 配额为一个逻辑核的 80%。[780 局模型的历史部署记录](neural-deployment-2026-09-11.json)中，推理进程峰值约 335 MiB，三房间基准的平均请求耗时约 27.7 ms、p95 约 40.9 ms。这些结果仅适用于当时的模型和负载。

租赁训练机的 3080 Ti 测试也不能证明公网 CPU 或当前本机能承载深层推理。短训时的显存、优化器和历史模型池开销，不等于导出后的在线推理内存。

训练结束后，对每个最终推理文件分别记录：

| 测量项 | 要回答的问题 |
| --- | --- |
| 冷启动、稳定与峰值 RSS | 保留现有服务后能否装下单个或多个常驻模型 |
| 单条及批量推理的 p50、p95、最大耗时 | 单次决策是否满足超时和房间等待预算 |
| 一名玩家对七个人机的完整招募回合 | 多步买卖、出牌和刷新能否在计时模式内完成 |
| 多房间并发的排队时间、CPU、内存及错误率 | 增加房间是否影响游戏服务及其他站点 |
| 超时、回退次数和实际应用的模型决策数 | 是否出现页面可玩、实际却持续使用脚本回退的情况 |

压测使用独立测试房间，从低并发开始，按资源限额运行。先填写结果，再确定每个模型的部署位置和并发上限；尚未测量的项保留为待测，不能凭参数量填写结论。

## 公网承载不足时用当前本机

64 层已按用户明确要求固定在当前本机计算，经公网后端转发。已验证三房间、八回合，1,794 次模型决策零错误、零回退。公网购买带宽为 3 Mbps，当前压缩请求发送预算为 512 kbps。其他两个模型的计算位置和并发预算仍须分别验证。

优先用持久的反向 SSH 隧道，将本机推理服务接到公网机器的回环端口。浏览器仍只访问公网游戏后端，不直接连接推理服务。网络抖动、请求体大小、批处理等待和往返延迟都计入房间耗时。

本机服务和隧道需要进程守护、重连、健康检查和有界请求队列；公网后端继续核对模型输入契约并校验输出。本机休眠、断网或重启时，应显示模型暂不可用，并按已说明的方式回退。

上线验证需覆盖模型选择的保存与恢复、不同模型的输入契约、GRU 隔离、超时和过期响应、隧道断开后的回退，以及计时房间的完整一局。完成这些验证后再开放多模型选择；当前已上线的 64 层固定转发继续使用独立冻结版本。
